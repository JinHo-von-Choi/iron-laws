# 정확도 측정 기록

이 문서는 오철칙의 탐지 정확도를 측정한 방법과 결과, 그리고 한계를 있는 그대로 기록한다.

## 1. 규칙별 사례 시험

`tests/` 아래에 규칙마다 양성(탐지해야 함)과 음성(탐지하면 안 됨) 사례를 언어별로 둔다.
- `test_rule_cases.py`: 행안부 구현단계 규칙(주입, 암호, 오류 처리, 메모리 등) 221건
- `test_ai_arch_typing_cases.py`: AI 생성 코드 보정, 구조, 타입 안전성 규칙 98건
- `test_regressions.py`: 실제 프로젝트 점검과 벤치마크에서 발견한 오탐·미탐을 고정한 회귀 사례와 억제·생성 파일·CLI 형식 시험
- `test_plan_features.py`: 분기 합류·반복 흐름, 문맥별 정제, 파일 간 해석, 진단, 기준선, 억제 만료, 설정 선택, 근거(evidence), 지원 행렬 시험
- `test_review_findings.py`: 외부 평가에서 재현된 결함(잘못된 입력의 통과 처리, 억제 구문 오인식, 싱크 시점의 변수 상태, API 인자 위치, XXE 설정 값, 템플릿 연결, 출력 안전성)을 전체 CLI 경로로 고정한 시험

사례는 실제 점검에서 확인한 오탐을 바탕으로 계속 늘린다.

## 2. 실제 프로젝트 점검을 통한 오탐 정리

Java, JavaScript, Python, C#, Go, Rust, PHP, C/C++ 오픈소스·자체 프로젝트 수천 개 파일을 점검해 CRITICAL·HIGH 지적을 직접 분류했다.
이 과정에서 다음을 고쳤다.
- 압축·생성 파일과 빌드 산출물 제외
- 명령행 인자(argv, stdin)를 웹 입력과 구분 (개발 도구 스크립트의 오탐 제거)
- 브라우저 스크립트의 `fetch`를 SSRF로 보던 오탐 제거
- 환경변수 이름 상수, 비밀 값 참조(`$VAR`)를 비밀로 보던 오탐 제거
- DDL, EF Core 보간 쿼리, 요청 본문 스트림 같은 안전한 패턴 제외
- 속성 이름(`import.meta.url`)이 변수로 오염되던 문제 수정

### 해석과 한계
- OWASP Benchmark는 안전한 사례를 일부러 도우미 클래스, 상수로 결정되는 분기, 컬렉션 경유로 감춰 정적 분석의 오탐을 유도한다. 오철칙은 함수 안의 흐름(분기 합류, 같은 파일 도우미 함수 요약, 문맥별 정제 함수 이름 인식)과 파일 간 호출(Python, JavaScript·TypeScript, Java static 메서드)을 추적하고, 객체 필드 흐름과 상수 조건 계산은 하지 않는다. Benchmark 사례는 도우미 클래스가 측정 대상 폴더 밖에 있어 파일 간 해석이 수치를 바꾸지 않는다. 그래서 FPR이 높다.
- `weakrand` 0%는 의도한 결과다. 오철칙은 토큰·인증번호처럼 보안 문맥에서 쓰인 난수만 지적하며, 문맥 없는 `Random`은 지적하지 않는다.
- `securecookie`는 Secure·HttpOnly 누락 여부를 사람이 확인해야 해서 `확인 필요`로만 보고한다.
- 함수 안의 흐름은 실행 순서를 따르며, 분기(if·switch·try)는 갈래별로 실행해 합치고 반복문은 두 번 돌려 반복 간 전달을 반영한다. 한 갈래에서만 안전하게 바뀐 변수는 오염된 채로 남고, 모든 갈래에서 안전하게 바뀐 변수만 깨끗해진다. 완전한 제어 흐름 그래프나 상수 조건 계산은 하지 않는다(OWASP Benchmark 오탐의 주된 원인).
- 같은 파일의 도우미 함수는 호출부에서 외부 입력이 매개변수로 넘어갈 때 함수 안의 싱크까지, 반환값이 오염되는지까지 추적한다(호출 깊이 4단계, 재귀·순환 호출은 오염된 인자가 넘어가면 오염으로 보고, 오염된 인자 없이 도는 재귀의 반환은 오염 없음에서 시작해 다른 반환 경로의 오염을 따른다. 4단계를 넘거나 한도에 걸린 함수는 깨끗하다고 보지 않고 인자의 오염이 결과로 전해진다고 본다). 다른 파일의 함수도 같은 방식으로 추적한다: Python은 import, JavaScript·TypeScript는 ESM(named·default·namespace·재내보내기 1단계)·CommonJS(`module.exports`, `exports.a`, `require` 구조분해)·상대 경로·tsconfig `paths` 단일 와일드카드 별칭, Java는 명시 import·같은 패키지·와일드카드 import로 찾은 클래스의 static 메서드와, 주입 필드의 형식(클래스, 또는 구현이 하나이거나 `@Primary`가 하나인 인터페이스)의 인스턴스 메서드를 따른다. 후보 파일·클래스가 둘 이상이거나 동적 `import()`·계산된 `require`처럼 대상을 정할 수 없으면 해석 공백으로 세어 보고서 `metadata.cross_file.by_language`의 `resolution_gap_rate`에 남긴다. `limits.max_cross_file_lookups`가 관심 지점마다의 상한이며 넘으면 진단으로 남긴다. 결과는 병렬 작업 프로세스 수와 무관하다. Java의 그 밖의 객체 메서드(지역 변수로 만든 객체 등), C#·Go 등 다른 언어는 파일을 넘는 추적이 없다. 실제 프로젝트에서 달라진 지적의 분류는 `docs/benchmark_results/xfile_js.json`, `xfile_java.json`에 있다.
- 이 측정에서 파일 간 해석과 분기 합류 도입 전후의 OWASP Benchmark 수치는 같았다(Benchmark는 한 파일 안에서 완결되는 사례라 새로 잡은 경로와 새 오탐이 모두 0건). 새 기능의 효과는 §1의 사례 시험과 실제 프로젝트 점검(WebGoat 도우미 함수 안 SQL 삽입 4건 신규 탐지, DVWA에서 이스케이프된 입력 7건이 CRITICAL에서 확인 필요로 하향)으로만 확인했다.
- 정제 함수는 프로젝트에 정의되어 있으면 이름이 아니라 본문 동작을 따르고, 외부 라이브러리 함수는 이름으로 판단하되 **도달하는 곳의 문맥(HTML·SQL·셸·경로·URL·LDAP·XPath·헤더)에 유효한 정제만** 인정한다. HTML 이스케이프는 SQL 삽입·명령어 삽입을 막지 못하고, `normalize`·`abspath`는 경로 이탈 검사 없이는 정제로 보지 않는다. 다만 이름이 맞다고 해서 실제로 안전한 것은 아니다(예: 따옴표 없는 숫자 문맥에서의 SQL 이스케이프).
- 이 결과는 Java에만 해당한다. 다른 언어는 §1의 사례 시험과 §2의 실제 프로젝트 점검으로만 확인했고, 공개 벤치마크 수치는 아직 없다.
- 이 수치를 국정원 인증 도구의 정확도와 비교하거나 감리 증빙으로 쓰면 안 된다.

### 자체 감사 후 추가한 제한 모델

Java SQL의 닫힌 문자열은 상수로만 끝나는 분기, 유일한 프로젝트 정적 도우미의 반환값, `java.util.List.of`와 상수 인덱스 `get`에 한해 추가 확인한다. 객체 변경·외부 호출로의 전달·동명 클래스/변수·미해석 반환값은 면제하지 않는다. 개발 사례와 이름·전파 경로가 다른 평가 사례를 별도 시험한다. 이는 일반적인 Java 파일 간 오염 추적이 아니며, 위 OWASP Benchmark 수치는 이 변경을 적용해 다시 측정하지 않았다. Java 경로 규칙으로 SQL의 정상 근거를 확대하지 않는다.

Python 경로 모델에는 `Path.mkdir`, `unlink`, `rmdir`, `rename`, `touch`를 추가했다. 상수 경로·외부 입력·호출자 없는 매개변수·임시 파일 생성값을 구분하며 미해석 값을 정상으로 바꾸지 않는다. 지원 행렬에는 양성·음성 사례가 모두 있는 Python 조합 여섯 칸을 추가했다.

CI는 전체 감사의 계열·호출·상태·미확정 원인별 공백과 분모, 정책 제외 사유를 산출물로 보관한다. 전체 감사는 HIGH 이상 차단을 유지하고, `tests/fixtures/trust_scope`의 명시된 Python 세 계열만 unknown·미검증 비율 0 및 계약 block을 강제한다. 비율 감소만으로 전체 분석 정확도가 개선됐다고 판정하지 않는다.

## 4. 패치 검증 기능의 표본 측정

근거 계약·패치 검증·회귀시험·승인 추적의 표본 측정과 v1.3.0 대비 결과는 [PATCH_VERIFICATION.md](PATCH_VERIFICATION.md) §6에 있다. 위 OWASP Benchmark(Java) 수치는 이 기능들을 넣기 전후로 달라지지 않았다.

### 4.1 의미 변형 사례집

정상·위험 짝에 의미를 바꾸지 않는 변형 6종(이름 바꾸기, 주석 넣기, 빈 줄, 관련 없는 함수를 뒤·앞에 추가, 따옴표 모양)을 적용해 판정이 뒤집히는지 본다. 개발용(`tests/semantic_corpus.py`)과 평가용(`tests/semantic_holdout.py`)은 (유형, 스타일)을 나눠 만들었다(개발용: flask·express·plain·plain-java, 평가용: django·php-raw·spring·fastapi). 원본 수와 변형 수, 위험 탐지와 정상 유지는 합치지 않고 따로 쓴다.

| 구분 | 원본 | 변형 | 위험 미탐 | 정상 오차단 | 판정 변화 | 확인 필요로만 나온 정상 |
|---|---|---|---|---|---|---|
| 개발용 검사 30쌍 | 위험 30·정상 30 | 위험 180·정상 180 | 0 | 0 | 0 | 42/210 |
| 평가용 검사 15쌍 | 위험 15·정상 15 | 위험 90·정상 90 | 0 | 0 | 0 | 7/105 |

- 승인 사례(개발용 6·평가용 3)는 위험한 승계 0, 불필요한 재검토 0이다. 출력·억제 사례(개발용 4·평가용 3)는 오처리 0이다.
- 평가용 사례가 실패하면 엔진을 고치고, 그 사례를 개발용으로 옮긴 뒤, 같은 유형의 새 평가용 사례로 바꾼다. 이력은 `tests/semantic_holdout.py`의 `MOVED_TO_DEV`에 있다.
- 확인 필요(unknown)는 판단을 보류한 것이다. 정상 사례에서는 따로 세고, 위험 변형이 확인 필요로만 나오면 탐지가 아니라 실패로 센다.
- 파일 경계를 넘는 변형 3종(외부 입력을 다른 파일의 그대로 돌려주는 함수에 통과시키기, 두 파일을 거치는 함수 사슬에 통과시키기, 외부 입력을 읽는 일 자체를 다른 파일의 함수로 옮기기)은 위 6종과 따로 kill-rate(잡아낸 위험 변형 수 / 만든 위험 변형 수)로 잰다. 적용할 수 없는 사례(Python·JavaScript·TypeScript 외 언어)는 변형 수에 넣지 않고 따로 센다. 개발용 위험 변형 81건·평가용 21건을 모두 잡았고(kill-rate 1.0), 정상 변형(개발용 63건·평가용 21건)을 막은 경우는 없다. 세 번째 변형은 호출 지점에 입력 표현이 남지 않아 파일 간 해석 없이는 잡을 수 없다.

### 4.3 수정 지시문 판별 비교(AI 수정 결과)

측정 도구는 `benchmarks/fix_prompt_ab.py`, 원시 결과는 `docs/benchmark_results/fix_prompt_ab.json`이다. 회귀시험 표본 21건(명령 실행·경로 접근·SQL 조립 각 7건)을 같은 점검 결과로 만든 두 판의 `fix-prompt` 지시문으로 AI에게 고치게 했다. 이전 판은 v1.5.0의 지시문이고, 현재 판은 금지 패턴(억제 주석, 시험 삭제, 예외 삼키기, 도우미로 옮기기)과 규칙별 '이렇게 고치지 마세요/이렇게 고치세요' 짝을 더한 지시문이다. 수정안은 `benchmarks/fix_loop.py`와 같은 분류로 검증했고, 결함 행동 제거는 확정한 회귀 명세를 docker 격리 실행으로 판정했다. |---|---|---|---|---|---|---|
| 이전 판(v1.5.0) | 13/21 | 18/21 | 14/21 | 7/7 · 4/7 · 3/7 | 1 | 2 |
| 현재 판 | 16/21 | 18/21 | 17/21 | 7/7 · 6/7 · 4/7 | 0 | 1 |

사례별로는 3건이 해결로 바뀌었고, 2건은 실패 유형만 바뀌었으며(정적 지적 잔존 ↔ 결함 행동 잔존), 해결에서 실패로 바뀐 사례는 없다. 표본이 작고 응답을 한 번씩만 받았으며 모델 하나의 결과라, 이 차이를 지시문의 효과로 단정하지 않는다. 명령 실행 계열은 두 판 모두 결함 행동 제거가 절반 남짓이라 지시문만으로 풀리지 않는 영역으로 본다.

## 5. 의존성 권고·성능·AI 공격면 규칙

### 5.1 의존성 권고(`iron-laws deps`)

- **OSV 서버 판정과의 일치**(`docs/benchmark_results/deps_osv_crosscheck.json`): 같은 (패키지, 버전)을 OSV 서버에 물어 비교했다. PyPI 10개 패키지·400개 버전은 버전 단위 일치율 96.25%, 오탐 0건, 놓친 것 15건이다. 15건은 모두 Git 커밋 범위가 있는 권고이고 도구는 이를 `판정 불가`로 표시한다. npm 10개 패키지·391개 버전은 전부 일치했다.
- **실제 잠금 파일**(`docs/benchmark_results/deps_real_locks.json`): 잠금 파일 40개(uv 7, poetry 2, package-lock 26, pnpm 5), 패키지 13,426개에서 도구가 취약으로 본 (패키지, 버전) 537건이 OSV 서버 판정과 모두 같았고 한쪽에만 있는 것은 없었다. `판정 불가`는 6건이다.
- 같은 권고 데이터를 쓰는 두 구현의 비교라서 OSV 데이터 자체의 오류는 잡지 못한다.

### 5.2 성능 규칙(PERF)

실제 프로젝트 점검 결과에서 규칙별 표본을 뽑아 하나씩 판정했다.

| 규칙 | 표본 판정 |
|---|---|
| PERF-102 중첩 반복·리스트 찾기 | 21건 중 6~7건이 해당 패턴(약 30%) |
| PERF-103 반복 안 인터넷 요청 | 3건 중 2건이 해당 패턴 |

PERF-102의 절반 이상은 문제가 아닌 지적이라 `확인 필요`로만 보고한다. 오탐은 고정 크기 목록, 대기·재시도·먼저 성공하면 멈추는 순차 요청, 한 묶음씩 처리하는 반복, 반복 항목에서 파생된 값을 도는 안쪽 반복, 편집 거리 같은 표 채우기 알고리즘에서 남는다. PERF-105(비동기 함수 안의 파일·프로세스 호출)는 시작 시 한 번 실행되는 코드도 지적할 수 있어, 요청마다 실행되는 경로인지 확인해야 한다.

### 5.3 AI 에이전트 공격면 규칙(AIA)

AIA-101·102·106은 양성·음성 사례 시험(`tests/test_ai_attack_cases.py`)으로 검증한다. 비밀 유출을 시키는 문장은 목적지(URL·주소)가 함께 있을 때만 지적한다. 실제 프로젝트 점검에서는 지적이 나온 사례가 없어 실제 환경의 정밀도는 측정하지 못했다.

### 6.2 Juliet Test Suite 1.3 (C/C++, C#)

측정 도구는 `benchmarks/juliet.py`이며, 오철칙 규칙과 대응하는 CWE만 잰다(대응표는 결과 파일의 `cwe_rule_map`). 범주별 수치는 `docs/benchmark_results/juliet_c.json`, `juliet_cs.json`에 있다. C/C++의 메모리 규칙(IL-514)은 `strcpy` 같은 위험 함수 호출을 안전 여부와 관계없이 알리는 패턴 규칙이라 bad·good 양쪽에 같이 걸려 TPR과 FPR이 같게 나온다. C#은 Juliet가 쓰는 입력 방식(`req.Params.Get`, `Console.ReadLine`)과 SQL 실행 방식(`CommandText` 속성 대입)이 소스·싱크 모델에 없어 대부분의 범주에서 탐지가 0이다.

### 6.3 Semgrep·CodeQL과의 같은 조건 비교

측정 도구는 `benchmarks/compare_tools.py`, 원시 결과는 `docs/benchmark_results/compare_tools.json`이다. 의미 변형 사례집의 위험·정상 짝과, 위험 코드의 외부 입력 읽기를 다른 파일 함수로 옮긴 우회 변형을 쓴다. 개발용 사례는 오철칙을 만들며 맞춘 사례라 공정한 비교는 평가용(holdout)이다.

| 도구 | 평가용 위험 탐지 | 평가용 정상 오탐 | 평가용 우회 거부 | 전체 위험 탐지 | 전체 정상 오탐 | 전체 우회 거부 |
|---|---|---|---|---|---|---|
| iron-laws 1.6.0 출시 전 개발 판 | 9/9 | 0/9 | 7/7 | 36/36 | 0/36 | 34/34 |
| semgrep 1.180.0 | 5/9 | 2/9 | 2/7 | 28/36 | 17/36 | 8/34 |
| codeql 2.27.2 | 0/9 | 1/9 | 0/7 | 19/36 | 11/36 | 19/34 |

사례는 합성 코드 조각이라 프레임워크 연결(Express 앱 생성, Django URL 연결 등)이 빠진 경우가 많다. CodeQL은 이런 연결로 외부 입력을 인식하므로 JavaScript 0건, Java 1건으로 실제 성능보다 낮게 나온다. Semgrep 규칙은 실행 시점의 레지스트리 `p/default`다. 이 비교는 같은 조건에서 각 도구가 어떻게 판정하는지 보여 주는 것이며, 실제 프로젝트에서의 우열을 보증하지 않는다.

### 6.4 CWE-Bench-Java(실제 오픈소스 CVE)

측정 도구는 `benchmarks/cwe_bench_java.py`, 데이터는 CWE-Bench-Java 커밋 `afe0ebd0adc237abb46255f9cd479b1d71819136`(120개 사례), 원시 결과는 `docs/benchmark_results/cwe_bench_java.json`이다. 사례마다 취약한 커밋과 수정 커밋의 프로젝트 전체를 점검하고, 데이터가 지목한 취약 메서드 안에 해당 규칙(CWE-22 → IL-502, CWE-78 → IL-504, CWE-79 → IL-505, CWE-94 → IL-503)의 지적이 있으면 취약한 쪽은 TP, 수정된 쪽은 FP로 센다. 확정은 확정 지적만, 전체는 확인 필요 지적까지 센 결과다.

| 분류 | 확정 TP/FN/FP/TN | 확정 재현율 | 확정 오탐률 | 전체 TP/FN/FP/TN | 분석하지 못함(취약/수정) |
|---|---|---|---|---|---|
| CWE-22 경로 조작 | 14/26/6/32 | 35.0% | 15.8% | 14/26/6/32 | 15 / 17 |
| CWE-78 명령 삽입 | 0/12/0/12 | 0.0% | 0.0% | 0/12/0/12 | 1 / 1 |
| CWE-79 XSS | 0/28/0/27 | 0.0% | 0.0% | 0/28/0/27 | 3 / 4 |
| CWE-94 코드 삽입 | 0/18/0/18 | 0.0% | 0.0% | 2/16/2/16 | 3 / 3 |

경로 조작에서 잡은 14건은 대부분 압축 해제 경로 조작(Zip Slip)과 웹 프레임워크 요청 경로(Flink `getPathParameter`)다. 놓친 사례는 대체로 다음과 같다.

- 라이브러리 함수 자체의 검증 결함: 공개 메서드의 매개변수가 입력이라 외부 입력 흐름이 코드에 없다(commons-io, ESAPI, myfaces, antisamy, json-sanitizer, sling-xss, hibernate-validator 등). CWE-79 사례의 다수가 XSS 방어 라이브러리 자체의 결함이다.
- 웹 요청이 아닌 입력: Jenkins 작업 설정 값(perfecto), 디렉터리 서비스의 그룹 이름(nifi), 라우트 정의(spring-cloud-gateway)처럼 프레임워크 고유의 입력 모델이 필요하다.
- 셸 삽입이 아닌 명령 결함: git 인자 삽입(git-client-plugin), 역직렬화를 거친 명령 실행(xstream), 스크립트 샌드박스 우회(Jenkins).
- 상속·추상 메서드를 거치는 흐름(plexus-archiver), 경로 API를 직접 부르지 않는 결함(retrofit, rocketmq, keycloak 등).

CWE-94의 확인 필요 2건(spring-cloud-gateway, spring-boot-admin)은 상수가 아닌 SpEL 식 평가를 짚었지만, 수정된 쪽도 같은 지적이 남아 결함 판과 수정 판을 가르지 못한다(수정은 평가 컨텍스트를 다른 함수에서 바꿨다). 경로 조작 수정 판의 오탐 6건은 검사가 다른 메서드에 있거나(DependencyCheck), 검사 뒤 같은 경로를 문자열로 다시 조립하거나(DSpace), 조건부로만 검사하는 약한 방어(zt-zip의 `..` 포함 시에만 검사)다. 대형 저장소(aws-sdk-java, Java 파일 약 22만 개)는 한 사례 점검에 약 70분이 걸렸다.

## 7. 재현

측정 결과에는 도구 버전, 데이터 커밋, 명령, 원시 건수(TP·FN·FP·TN)를 함께 적는다. 원시 결과는 `docs/benchmark_results/owasp_confirmed.json`과 `owasp_all.json`에 있다.
점수는 같은 데이터 커밋끼리만 비교하고, 한 언어의 점수를 전체 정확도로 합산하지 않는다.

```bash
git clone https://github.com/OWASP-Benchmark/BenchmarkJava.git
git -C BenchmarkJava checkout 8b67a88d73b2594570fc21150705283de884620b
uv run python benchmarks/owasp_benchmark.py BenchmarkJava confirmed docs/benchmark_results/owasp_confirmed.json
uv run python benchmarks/owasp_benchmark.py BenchmarkJava all docs/benchmark_results/owasp_all.json
```

수정 지시문 비교(§4.3)는 AI 명령을 사용자가 정한다. 응답은 작업 폴더에 남아 같은 지시문이면 다시 부르지 않는다.

```bash
git show v1.5.0:src/iron_laws/reporters/prompt.py > prompt_previous.py
uv run python benchmarks/fix_prompt_ab.py work prompt_previous.py docs/benchmark_results/fix_prompt_ab.json \
  --ai-cmd="claude -p --tools '' --strict-mcp-config --setting-sources '' --no-session-persistence --model sonnet" --runner=docker
```

처리 시간과 최대 메모리는 같은 장비·같은 저장소에서 수정 전후를 비교해 기록한다. 처리 시간은 작업 프로세스 수를 고정하고 3회 반복한 중앙값이다(`benchmarks/bench_common.py`의 `timed_scan`). 이번 변경(흐름 분석 교체, 파일 간 해석)의 측정: flask(소스 약 5천 파일 규모) 4.9초 → 5.4초, WebGoat 8.9초 → 9.3초, 최대 메모리 약 80~120MB로 큰 차이가 없었다. 속도 향상을 약속하지 않는다.
