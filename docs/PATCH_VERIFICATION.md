# AI가 만든 패치의 로컬 검증과 승인 근거

오철칙은 AI가 만든 패치를 받아서 **무엇을 확인했고 무엇을 확인하지 못했는지**를 승인 판단에서 사라지지 않게 남기는 도구로 쓸 수 있습니다.
이 문서는 그 흐름의 구성, 안전 경계, 측정한 것과 측정하지 못한 것을 정리합니다.

> 이 문서의 '통과'는 지정된 검사 계약을 충족했다는 뜻입니다. 안전성, 취약점 부재, 완전한 기능 동등성을 증명하지 않습니다.
> 기록에 남는 해시는 무결성(변조 탐지) 근거일 뿐 코드의 안전성이나 승인자의 진위를 증명하지 않습니다.

## 흐름

```
점검 → (수정 요청: fix-prompt) → AI 패치 → verify-patch → 사람 승인(approvals) → 이후 변경 때 승인 전제 재확인
                                      └ 회귀시험(regression): 결함을 구별하는 최소 시험
```

모델이 낸 자기평가는 어디에도 입력으로 쓰지 않습니다. 결과는 도구가 직접 실행하고 측정한 것만 담습니다.
원본 수정·커밋·게시·병합은 검증과 별도 권한이며 도구는 하지 않습니다.

## 1. 근거 계약과 검사 공백 장부

검사가 끝났다(`scan_status`)는 것과 요구한 근거가 충족됐다(`contract_status`)는 것은 별개입니다. 경고 0건은 자동 승인이 아닙니다.

- 계약 파일(`--contract`)은 팀이 선언하는 신뢰 정책입니다. 첫 범위는 **Python의 명령 실행·경로 접근·SQL 조립** 세 계열입니다.
- 장부(`coverage_ledger`)는 파일과 보안 관심 지점(호출)마다 상태를 기록합니다.

| 상태 | 뜻 |
|---|---|
| `evidence_met` 근거 충족 | 모든 입력이 상수·닫힌 값으로 확인됐거나, 외부 입력 도달이 확인돼 지적으로 보고됨. 프로그램 전체가 안전하다는 뜻이 아님 |
| `unsupported` 미지원 | 호출은 보이는데 규칙에 모델이 없음 |
| `unresolved` 해석 미확정 | 입력 출처를 확정하지 못함(호출자 없는 매개변수, 미해석 호출, 객체 속성 등). **깨끗함으로 바꾸지 않음** |
| `budget_exceeded` 예산 초과 | 파일 간·함수 간 해석 한도(`limits.max_cross_file_lookups`)에 도달 |
| `policy_excluded` 정책 제외 | 계약의 제외 경로(사유 필수) 또는 사유 있는 억제 주석이 제외 |

- 단일 안전 점수는 만들지 않습니다. 발견한 관심 지점 수와 분류하지 못한 파일(`unclassified`)을 분모로 함께 공개합니다. 분류하지 못한 파일을 조용히 제외해 수치를 높이지 않습니다.
- `mode: report`(기본)는 공백을 모으기만 합니다. `mode: block`은 **필수로 지정한 계열**의 미충족(`block_on` 상태)과 분류하지 못한 변경 파일이 있으면 실패(종료코드 1)합니다. 모든 `unresolved`를 취약점으로 보거나 무조건 막지 않습니다.
- 계약 파일이 이번 변경에 포함되어 있으면(`--changed-since`) 후보 변경이 정책을 바꾼 것이므로 `policy_change_review`로 표시합니다.
- 장부의 한계: 관심 지점은 호출 이름으로 찾습니다. import 별칭, `getattr` 같은 동적 호출, 프레임워크가 감춘 호출은 지점으로 발견되지 않을 수 있습니다.

```bash
iron-laws check . --contract .iron-laws-contract.yml --changed-since origin/main
iron-laws audit . --format json     # coverage_ledger: 판정·분모·해시
```

CLI·JSON·SARIF(`runs[].properties.coverageLedger`, invocation notification)·마크다운·`fix-prompt`가 같은 코드·설정·도구 해시에서 같은 판정과 범위를 보존합니다.

## 2. 패치 검증과 Receipt (`verify-patch`)

```bash
iron-laws verify-patch ./proj --patch fix.diff --finding IL-504@app.py:6 \
  --runner docker --image iron-laws-verify:py313 \
  --test-cmd python --test-cmd -m --test-cmd pytest --test-cmd -q -o receipt.json
iron-laws verify-patch ./proj --patch fix.diff --replay receipt.json   # 같은 입력·조건으로 깨끗한 작업영역에서 재실행
```

종료코드: `0` 검증 항목 통과, `1` 검증 실패, `2` 판정 불가·입력 오류.

검사 항목(각각 `pass` 검증 항목 통과 / `fail` 검증 실패 / `not_run` 미실행 / `unknown` 판정 불가 — 실패와 미실행을 같은 값으로 합치지 않습니다):

| 항목 | 내용 |
|---|---|
| 입력 고정 | 원본·후보 트리의 내용 해시. dirty working tree도 실제 파일 내용으로 고정. 작업영역 밖을 가리키는 symlink·특수 파일은 위험으로 기록 |
| patch 안전성 | 경로 이탈·절대 경로·`.git`·훅·바이너리·symlink 생성·크기 상한, 적용 가능성 |
| 정책·시험 동결 | 설정·계약·실행 정책·baseline·승인 기록·**원본 시험**은 후보가 바꾸지 못한다. 바꾸려는 시도는 적용하지 않고 원본으로 되돌려 실행 |
| 우회 변경 | 시험 삭제·함수 감소·내용 수정, skip/xfail 증가, 단언 약화, 무시 주석(`ignore`·`nosec`·`noqa` 등) 추가, 설정 약화(`disabled_rules`·`excludes`·`fail_on` 완화 등), baseline 재생성, 시험 기반 파일(`conftest.py` 등) 변경 |
| 동일 조건 정적 검사 | 같은 규칙·설정·상한으로 원본과 후보를 검사. 후보가 새로 단 억제 주석은 적용하지 않음 |
| 대상 지적 해소 | 지적이 사라졌더라도 파일 삭제·무시 주석·정책 변경이 함께 있으면 수정으로 인정하지 않음 |
| 새 지적 / 검사 공백 | 실패 기준 이상의 새 지적, 늘어난 검사 공백 |
| 변경 범위 | 대상 파일 포함 여부, 파일 수 상한, 허용 경로 |
| 기존 시험 | 원본과 후보를 같은 명령으로 격리 실행. 원본이 이미 실패하거나, 후보에서 0건·skip 증가·통과 수 감소가 있으면 통과가 아님 |
| 회귀시험 | 아래 3번 |

Receipt에는 원본·후보 트리 해시, patch 해시, 도구·규칙셋·설정·계약·실행 정책 해시, 실행 환경(이미지 ID 포함), 항목별 실행 여부·결과·시간·상한 도달 여부, 우회 변경, 지적·공백 비교가 들어갑니다. 원문 프롬프트·전체 소스·전체 로그는 저장하지 않으며 시험 출력은 마지막 일부만 비밀을 가려서 남깁니다.

기본 정책은 시험 실행이 **필수**입니다. 격리 환경을 얻지 못하면 시험을 실행하지 않고 `판정 불가`로 남깁니다(`--no-require-tests`로 완화 가능, 그 경우에도 `미실행`이 기록에 남습니다).

## 3. 결함을 구별하는 최소 회귀시험 (`regression`)

```bash
iron-laws regression propose ./proj --finding IL-504@app.py -o spec.yml   # 제안: 근거 아님, confirmed: false
# 사람이 payload·benign·expect·fake_sink를 확인하고 confirmed: true로 바꾼다
iron-laws regression check ./proj --patch fix.diff --spec spec.yml --runner docker --image ...
iron-laws verify-patch ./proj --patch fix.diff --finding ... --regression spec.yml
```

- 제안은 지적의 입력·전파·싱크 근거에서 template 기반으로 만듭니다. 지원 범위는 Python의 명령 실행(IL-504)·경로 접근(IL-502)·SQL 조립(IL-501), **모듈 수준 함수**(요청 값 또는 매개변수가 입력)입니다. 클래스 메서드, async, Django·FastAPI, 전역 연결 객체는 이유와 함께 거절합니다.
- 사람이 확정한 명세만 신뢰된 harness가 실행합니다. harness는 실제 셸·네트워크·작업영역 밖 파일·DB에 접근하지 않고 mock sink(`os.system`·`subprocess`·`open`·커서 등)에서 호출을 **기록만** 합니다.
- 검증 순서: ① 원본에서 결함 때문에 실패(세 번 반복 일치), ② 정상 대조군 통과, ③ 후보에서 통과하고 정상 대조군 유지(세 번 반복 일치), ④ 수정 hunk를 되돌리거나 추가한 문장을 지운 mutant 중 유효한 것에서 다시 실패(killed / survived / invalid 구분).
- 환경 실패(import 오류·의존성 누락·문법 오류)는 결함 재현으로 세지 않습니다. 정상 입력까지 막는 수정(위험 기능을 전부 막는 것)은 정답이 아닙니다. 원본이 재현되지 않거나 의미 있는 mutant가 없으면 시험 후보로 남기고 통과로 보지 않습니다.
- 정적 분석기의 탐지 결과만 assertion으로 쓰는 시험은 만들지 않습니다. 시험은 코드를 실제로 실행해 관측한 동작만 판정합니다.
- 한계: 후보 코드가 같은 프로세스 안에서 harness의 결과를 조작하는 것까지 막지 못합니다. 살아남은 mutant는 수정과 무관하거나 기능적으로 동등한 변경일 수 있어 사람이 검토해야 합니다.

## 4. 격리 실행 경계

저장소, patch, 시험, 주석, 모델 출력, 로그는 모두 비신뢰 입력입니다.

| 경계 | 통제 |
|---|---|
| 원본과 후보 | 원본 스냅샷은 읽기 전용, 후보는 별도 임시 작업영역. 정책·원본 시험·승인 기록은 후보의 쓰기 권한 밖 |
| 실행 환경 | docker(`--network none`, 읽기 전용 루트, `--cap-drop ALL`, `no-new-privileges`, 비특권 사용자 65534, `--pids-limit`, CPU·메모리 상한) 또는 bubblewrap. 마운트는 작업영역 하나뿐(host home·SSH agent·cloud 자격증명·Docker socket 없음) |
| 네트워크·의존성 | 시험 중 네트워크 없음, 이미지는 `--pull never`(준비 단계에서 미리 받아 둠) |
| 명령 | 신뢰된 명령 목록(argv)만. shell 문자열·`sh -c` 거부 |
| 자원 | 후보당 기본 2 CPU·2 GiB·180초·출력 1 MiB·최대 2회(실행기 오류만 재시도). 상한 도달(`timeout`/`output_limit`/`resource_limit`)은 시험 실패가 아니라 `판정 불가` |
| 격리 실패 | **호스트 실행으로 자동 대체하지 않는다.** 시험을 실행하지 않고 `판정 불가` |

실제 적대적 입력(네트워크 접속, 작업영역 밖 쓰기, `docker.sock`·`~/.ssh` 탐색, 포크 폭탄, 메모리 폭주, 무한 대기, 출력 폭주, 로그에 심은 지시문)으로 시험했을 때 모두 차단되거나 상한으로 끝났고 판정은 종료코드로만 정해졌습니다(`tests/test_stage3_verify.py`의 docker 시험).
컨테이너만으로 완전한 격리를 보증하지 않습니다. 고위험 비신뢰 코드에는 microVM 같은 추가 경계를 검토해야 합니다. 다중 OS 실행 sandbox(Windows·macOS)는 이번 범위에 없습니다.

격리 실행 이미지는 준비 단계에서 만듭니다(예):

```dockerfile
FROM python:3.13-slim
RUN pip install --no-cache-dir pytest
```

신뢰된 실행 정책은 원본 저장소의 `.iron-laws-runner.yml`(이미지, 허용 명령, 상한)에서 읽습니다.

## 5. 승인 기록과 변경 유효성 (`approvals`)

```bash
iron-laws approvals add . --finding IL-504@app.py --reason "관리자 전용·입력 검증됨" --reviewer 홍길동 \
  --expires 2027-03-31 --receipt receipt.json --minutes 12 --store /trusted/path/approvals.jsonl
iron-laws check . --approvals /trusted/path/approvals.jsonl          # 유효한 승인만 받아들임
iron-laws approvals status .   --store ...                            # 승인별 유효성: 유효 / 재검토 필요 / 해소 / 미확인 / 철회
iron-laws approvals queue .    --store ...                            # 검토 대기열
iron-laws approvals stats      --store ...                            # 검토 시간 계측
```

- 승인은 baseline(기존 지적 관리 데이터)과 **별개**입니다. baseline 항목은 사람의 승인으로 자동 승격되지 않습니다(`baseline migrate`도 `kind: debt`로만 옮깁니다).
- 승인 기록에는 사유, 대상(규칙·경로·함수·지문), 유효기간, 승인 당시 정책(계약·설정·규칙셋·도구) 해시, 검토한 흐름(역할·위치·변수 이름), 의존성 지문, Receipt 해시, 검토 시간이 남습니다. **코드 원문·비밀값은 담지 않습니다.**
- 승인 당시 전제(의존성 지문): 흐름의 함수 본문 지문(주석·공백 제외, 데코레이터 포함), 흐름이 호출하는 프로젝트 함수(깊이 3)의 본문 지문, 호출자 집합, 정제·검증 호출, 싱크 함수의 문자열 상수(접근 범위·질의 틀).
- 이후 변경 처리:

| 변화 | 처리 |
|---|---|
| 줄 이동·공백·주석 | 유지 |
| 파일 이동 | 옛 경로가 사라졌고 일대일로 맺어질 때만 유지 |
| 취약 코드 복제 | 원본이 남아 있는 동안 복제본은 승인을 물려받지 않음(새 검토 대상) |
| 새 호출자, 싱크·source·호출 함수·정제 함수 변경, 접근 범위 변경 | 해당 승인만 재검토 |
| 규칙 판정 의미(`version`)·계약·점검 설정 변경, 유효기간 경과, 철회 | 재검토 |
| 파일 없음·읽기 실패 | 해소로 보지 않고 미확인 |

- 기록은 추가 전용 JSONL이며 각 줄이 앞 줄의 해시를 이어받습니다(`approvals verify`). 이는 변조 탐지용입니다. 검토자 이름은 인증되지 않은 표기입니다. 기록 파일을 바꿀 수 있는 공격자가 있는 환경에서는 승인 인증을 주장하지 않으며, 조직 서명은 후속 범위입니다. 기록 파일은 후보 변경이 쓸 수 없는 위치에 두십시오(저장소 안에 있으면 `verify-patch`가 원본으로 되돌려 실행하고 우회 변경으로 표시합니다).
- 보존기간과 삭제: `approvals forget`(삭제 표시), `approvals prune --before DATE --yes`(만료·철회·삭제 표시된 기록을 파일에서 지우고 해시 연결을 새로 만듦, 되돌릴 수 없음). 프로젝트별 검토 판단을 동의 없이 자동 수집하거나 외부로 보내지 않습니다.
- 영향 분석은 구문 구조와 호출 요약을 쓰는 보수적 판정이며 의미 동등성을 주장하지 않습니다. Python 외 언어는 같은 파일 안 호출만 요약합니다.

## 6. 측정한 것과 측정하지 못한 것

**아직 하지 못한 것(계획에는 있으나 이 저장소의 시험으로는 확인할 수 없는 것):**
