# 오철칙 사용 지침

목표는 세 가지입니다. 같은 점검을 되풀이하지 않고, 지적을 한 번에 분류해 고치고, 끝낼 때 통과 근거를 남깁니다.

## 1. 시작할 때

- `iron-laws --version`으로 설치를 확인합니다. 없으면 사용자에게 설치 명령(`uv tool install git+https://github.com/JinHo-von-Choi/iron-laws.git`)을 알리고 기다립니다. 직접 설치하지 않습니다.
- 플러그인 훅이 켜져 있으면 세션 시작 때 프로젝트 언어의 HIGH 이상 규칙이 지침으로 들어옵니다. 코드를 쓸 때 그 지침을 기준으로 삼습니다. 훅이 없으면 `iron-laws guidelines export --lang python,typescript`처럼 프로젝트 언어로 받아 봅니다.
- 점검 폴더의 `.iron-laws.yml`에서 `fail_on`, `excludes`, `disabled_rules`, `limits`를 읽어 둡니다. 이 파일은 읽기만 합니다(5절).

## 2. 편집 중에는 좁게 점검한다

| 상황 | 할 일 |
|---|---|
| 파일을 고친 직후 | 훅이 있으면 자동으로 점검됩니다. 없으면 `iron-laws check <고친 파일>` |
| 여러 파일, 브랜치 작업 | `iron-laws check . --changed-since origin/main --limit 0` |
| 작업을 끝내기 전 | `iron-laws check .`를 한 번 |
| 보고서가 필요할 때만 | `iron-laws audit . --format markdown -o <점검 폴더 밖 경로>` |

- 편집 직후 훅이 지적을 돌려주면 다른 일로 넘어가기 전에 그 지적부터 처리합니다.
- 코드가 바뀌지 않았으면 같은 점검을 다시 돌리지 않습니다. 결과는 같습니다.
- MCP 도구(`check`, `explain`, `fix_prompt`, `verify_patch`, `deps`)가 보이면 셸 명령 대신 써도 됩니다. 입력 이름은 CLI 옵션과 같습니다.

## 3. 지적을 처리하는 순서

1. 전부 봅니다. `check`는 기본으로 50건만 보여 주므로 `--limit 0`을 붙입니다.
2. 심각도 순으로, 같은 규칙끼리 묶어서 처리합니다. 한 건씩 고치고 다시 점검하는 일을 반복하지 않습니다.
3. 지적마다 판정합니다.
   - `확정`: 입력에서 위험 호출까지 이어진 근거(`판단 근거` 줄)가 있습니다. 코드를 고칩니다.
   - `확인 필요`: 근거가 부족합니다. 해당 코드를 읽고 실제 결함인지 판단합니다.
4. 고치는 방법은 지적의 `고치는 방법` 줄과 `iron-laws explain <규칙 ID>`에 있습니다. 지적이 많으면 `iron-laws fix-prompt .`로 묶은 수정 지시문을 받습니다.
5. 오탐이거나 의도한 예외면 사유를 적은 억제 주석을 답니다. 사유가 없는 주석은 무시됩니다.

   ```python
   except ImportError:  # iron-laws: ignore[IL-301] 선택 의존성이 없으면 이 기능을 끈다
   ```

   ```python
   # iron-laws: ignore-file[IL-102] 취약 알고리즘을 탐지하는 패턴 정의 파일   (파일 상단 30줄 안)
   ```

   - 사유에는 그 코드가 왜 안전한지, 또는 왜 이렇게 둬야 하는지를 씁니다.
   - 기한이 있는 예외는 `until=2026-12-31`을 붙입니다. 만료되면 지적이 다시 나옵니다.
   - 코드를 다른 파일로 옮기면 억제 주석도 함께 옮깁니다. 남은 주석은 '쓰이지 않은 억제'로 보고됩니다.

## 4. 판단이 필요한 흔한 지적

아래 경우는 지적이 나와도 결함이 아닐 수 있습니다. 코드를 읽고 정합니다.

| 지적 | 결함이 아닐 수 있는 경우 | 처리 |
|---|---|---|
| IL-502 등 외부 입력 계열 | 웹 요청이 아닌 객체의 변수·매개변수 이름이 `request`라서 `request.path` 같은 속성을 외부 입력으로 읽은 경우 | 객체가 실제로 웹 요청이 아니면 이름을 내용에 맞게 바꿉니다(`inputs`, `options` 등) |
| PERF-102 | 입력 크기와 관계없는 고정 크기 목록(패턴 몇 개, 설정 항목)을 도는 반복 | 사유를 적어 억제합니다. 입력에 따라 커지는 목록이면 집합·사전 조회로 바꿉니다 |
| ARC-205 | 파서 노드 이름, JSON 키처럼 외부 형식이 정한 문자열의 반복 | 상수로 모을지 판단하고, 형식 그대로가 맞으면 억제합니다 |
| ARC-208 | JSON을 읽고 쓰는 경계 함수가 dict를 그대로 받거나 돌려주는 경우 | 경계 밖으로 dict가 퍼지면 모델로 바꾸고, 경계 함수에만 머물면 억제합니다 |
| 보안 규칙 전반 | 탐지 패턴을 정의하는 파일이 그 패턴을 문자열로 담은 경우 | `ignore-file`로 파일 단위 억제합니다 |
| ARC-201 | 공개 생성자처럼 인자 목록을 바꾸면 호출자가 깨지는 함수 | 내부 호출을 옵션 객체로 묶을 수 있는지 먼저 보고, 안 되면 사유를 적어 억제합니다 |

긴 함수(ARC-201), 순환 참조(ARC-203), 중복 함수(ARC-204)는 대부분 실제 개선 대상입니다. 함수를 나누거나 공용 부분을 별도 모듈로 옮겨 고칩니다.

## 5. 하지 않는 것

- `.iron-laws.yml`을 고쳐 지적을 없애지 않습니다. `fail_on` 올리기, `excludes`·`disabled_rules` 추가, `limits` 늘리기가 여기에 해당하며, 훅이 이런 편집을 사용자에게 알립니다. 기준을 바꿔야 한다고 판단하면 이유를 들어 사용자에게 묻습니다.
- 실제 결함을 탐지에서 빼려고 이름을 바꾸거나 코드 모양만 바꾸지 않습니다.
- 기준선(`baseline create`)과 승인 기록(`approvals add`)은 기존 지적을 받아들인다는 사람의 결정입니다. 사용자가 요청했을 때만 만듭니다.
- 시험을 지우거나 약하게 바꿔 통과를 만들지 않습니다.

## 6. 고친 뒤 확인

- 고친 파일을 다시 점검해 그 지적이 사라졌는지 봅니다.
- 명령 실행·경로·SQL·SSRF·XSS 계열은 지적이 사라져도 결함 동작이 남을 수 있습니다. 실행 검증이 필요하면 회귀시험 초안을 만들고 사람이 확인한 뒤 `verify-patch`로 격리 실행합니다.

  ```bash
  iron-laws regression propose . --finding IL-504@app.py:8 -o ../spec.yml
  iron-laws verify-patch . --patch ../fix.diff --finding IL-504@app.py:8 --runner docker --image <시험 이미지> \
    --test-cmd python --test-cmd -m --test-cmd pytest --test-cmd -q -o ../receipt.json
  ```

  docker나 시험 이미지가 없으면 실행 검증을 하지 않았다고 보고합니다.
- patch, 보고서, 검증 기록, 승인 기록은 점검 폴더 밖에 둡니다. 안에 두면 다음 점검 대상이 됩니다.

## 7. 끝내기 전

`iron-laws check .`를 한 번 돌리고 종료코드로 판단합니다.

| 종료코드 | 뜻 |
|---|---|
| 0 | 기준 심각도 이상의 지적 없음 |
| 1 | 기준 이상 지적이 있거나 신뢰 지표가 상한을 넘음 |
| 2 | 점검을 끝까지 하지 못함(설정 오류, 파일 읽기 실패, 점검한 파일 0개, 시간 초과). 통과가 아닙니다 |

종료 직전 훅이 켜져 있으면 세션에서 편집한 파일을 다시 점검해, 지적이 남아 있을 때 종료를 막고 지적을 돌려줍니다. 그 지적을 고친 뒤 끝냅니다.

## 8. 보고

- 지적 수, 고친 것, 억제한 것과 그 사유, 사용자가 판단할 것을 나눠 씁니다.
- 출력의 신뢰 지표(미검증 (규칙, 언어) 조합 비율, 분석 unknown 비율)를 함께 적습니다. 미검증 조합에서 지적이 없다는 것은 통과 근거가 아닙니다.
- '통과'는 정한 검사 조건을 채웠다는 뜻입니다. 코드가 안전하다는 보증이 아닙니다. 돌리지 않은 검사(실행 검증, 의존성 점검 등)는 돌리지 않았다고 적습니다.
